# Jira history

## Назначение

По ключу задачи → CLI тянет issue + changelog → отчёт в `reports/history/` → ответ по JSON/Markdown.

С `--with-git` дополнительно ищет связанные MR через отдельный Git-клиент (GitLab/GitHub) и добавляет события в хронологию + блок анализа MR.

Токены Jira/Git не читать и не показывать. Модель `Issue` не менять. Старые отчёты не перезаписывать и не удалять.

## Команда пользователя

```text
Расскажи историю CAT2-1234
Расскажи историю CAT2-1234 с MR
История CAT2-1234 --with-git
```

Если пользователь просит MR / git / ревью / merge request — запускать с `--with-git`.

## CLI

Запускать из корня репозитория:

```bash
python3 scripts/cli/get_issue_history.py CAT2-1234
python3 scripts/cli/get_issue_history.py CAT2-1234 --format both
python3 scripts/cli/get_issue_history.py CAT2-1234 --with-git
```

Если текущая директория другая:

```bash
python3 scripts/cli/get_issue_history.py CAT2-1234 --with-git
```

Перед первым запуском: `pip3 install -r scripts/requirements.txt`. Скрипт может работать несколько секунд (с `--with-git` — дольше).

Имя файла: `{YYYY-MM-DD}_{HH-MM}__{KEY}__history.json` (+ `.md`) в `reports/history/`.

Для `--with-git` в `.env` нужен отдельный `GITLAB_PAT` (или `GITHUB_PAT`), не `JIRA_PAT`.

## Когда ходить в Jira / Git

| Ситуация | Действие |
|----------|----------|
| Есть отчёт по этой задаче **< 8 ч** и тот же режим (с/без git) | Читать JSON, скрипт не запускать |
| Уточнение по той же истории | Тот же отчёт |
| Отчёт старше 8 ч, «обнови / пересобери», или нужен git, а в отчёте его нет | Новый запуск CLI → **новый** файл |

Считать режимы разными: отчёт без `git` не подходит, если пользователь просит анализ MR.

## Что показать в ответе

1. Ключ, название, ссылка, текущий статус и исполнитель
2. **Хронология** — по `timeline` (создание, статусы, assignee, оценка, Sprint/FixVersion, блокировки, важные комментарии; при `--with-git` ещё события MR)
3. **Циклы** — блок `cycles`, если задача ходила туда-сюда между одними и теми же статусами
4. **Возвраты** — `returns` / `summary.returns_count`
5. **Merge Request** — если в отчёте есть `git` / `mr_analysis` (или явное `reason`, почему MR нет)
6. **Итоговое состояние** — `final_state`
7. **Резюме** — дни в работе, смены исполнителя, возвраты, время до первой разработки, время до закрытия

Цифры — только из отчёта. Ссылки: `[CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)`.

### Блок MR (если был `--with-git`)

Для каждого MR из `merge_requests[]` / markdown-секции:

- автор, статус, даты создания / merge / закрытия
- время до первого ревью, время от первого замечания до исправления
- reviewers, число замечаний, циклы исправление → повторное ревью
- классификация замечаний (без ботов)
- поведение автора: только **факты / наблюдения / вопросы**, без выводов о квалификации

Если `git.ok == false` или MR не найдены — показать `git.reason` и продолжить обычный Jira-разбор.

## Что читается из JSON

- `timeline[]` — группы `{at, author, events[]}`
- `cycles[]` — `{pattern, statuses, started_at, ended_at}`
- `returns[]`
- `summary` — `days_in_work`, `assignee_changes`, `returns_count`, `days_to_first_development`, `days_to_close`
- `final_state`
- `issue` — краткие поля задачи (не полная модель для правок)
- `git` — `{enabled, ok, provider, reason}` (только при `--with-git`)
- `merge_requests[]` / `mr_analysis` — детали MR

Шум (Rank, RemoteIssueLink, worklog, description и т.п.) уже отфильтрован в отчёте.

## Чего не делать

- Не просить токены и не коммитить `.env`
- Не смешивать Git-токен с Jira-токеном и не выводить их в логах/ответах
- Не менять `models/issue.py` / структуру `Issue`
- Не дублировать HTTP-клиенты (Jira → `jira_client`, Git → `git_client`)
- Не ходить в Git без `--with-git` / без явного запроса пользователя про MR
- Не перезапускать скрипт при уточнениях, если отчёт свежий и в нужном режиме
- Не додумывать события, которых нет в JSON
- Не делать выводы о личности/мотивации/квалификации по одному MR
