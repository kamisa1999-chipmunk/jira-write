# Чек-лист закрытия SA-задачи

Копия для этого скилла. Если у команды есть более новый канон — читать его, не этот файл. В описание SA-задачи в Jira копировать wiki-версию: [checklist-close-sa-jira.txt](./checklist-close-sa-jira.txt) (режим «текст», не визуальный редактор).

Для каждого пункта указать:

- `[x]` / в Jira вписать `/` в `()` → `(/)` — выполнено (не `x`: это красный крестик «не выполнено»);
- `не относится: …` — если пункт неприменим, с указанием причины.

Статус «не относится» без причины не считается заполненным.

Ревью тимлида **выборочное**: задача проверяется на соответствие критериям чек-листа, без обязательной повторной проверки всей аналитики «с нуля».

### 1. Схема взаимодействия

Схема взаимодействия требуется, если в задаче участвует более одного компонента или системы.

- [ ] Если взаимодействуют несколько компонентов, есть схема с указанием участников взаимодействия и последовательности вызовов. Если взаимодействие включает несколько систем или независимых частей backend-логики, схема декомпозирована на соответствующие части и отражена в документации соответствующих backend-компонентов.



### 2. Сценарии и точки входа

Раздел применяется к клиентской части задачи, если существуют пользовательские экраны или иные точки входа.

- [ ] Перечислены все точки входа, затронутые изменением; для каждой описана последовательность: действие пользователя → реакция системы → ожидаемый результат.
- [ ] Если поведение различается между точками входа, Web/mobile или другими платформами, отличающиеся сценарии описаны отдельно.
- [ ] Если изменяемый метод или компонент вызывается не непосредственно из точки входа, описан путь взаимодействия до него.



### 3. Спецификации и шаблоны

Свериться со [списком шаблонов](https://confluence.goldapple.ru/pages/viewpage.action?pageId=640047269).

- [ ] Для каждого затронутого типа документации используется соответствующий утверждённый шаблон. Указать только затронутые типы; остальные не заполнять. Страница фичи — в подразделе ниже.
  - затронуто: …
  - Отображение на экране → [Шаблон. UI спецификации](https://confluence.goldapple.ru/pages/viewpage.action?pageId=762574742)
  - HTTP-метод → [Шаблон.Описание BACK-методы (HTTP)](https://confluence.goldapple.ru/pages/viewpage.action?pageId=649174595)
  - gRPC → [Шаблон.Описание BACK-методы (gRPC)](https://confluence.goldapple.ru/pages/viewpage.action?pageId=721139215)
  - Топик Kafka → [Шаблон.Описание топика](https://confluence.goldapple.ru/pages/viewpage.action?pageId=671395204)
  - Коллекция / БД → [Шаблон.Описание коллекции](https://confluence.goldapple.ru/pages/viewpage.action?pageId=662138588)
  - Админка → [Шаблон.Документация Plaid Admin](https://confluence.goldapple.ru/pages/viewpage.action?pageId=700188117); методы админки оформлены отдельными страницами по шаблону HTTP, со ссылками из документации админки.
- [ ] Если для типа документации нет отдельного утверждённого шаблона, в качестве основы используются существующие спецификации с аналогичным поведением или типом реализации. Такая документация должна содержать всю информацию, необходимую для реализации конкретного изменения: используемые данные, правила их обработки, условия выполнения и взаимодействие компонентов.
- [ ] Если в рамках задачи изменяется соответствующий объект, его страница должна быть создана или актуализирована.

- [ ] Если в задаче изменяется аналитика, отправляемая с frontend, для каждого события указаны условие отправки, набор передаваемых полей и источник значения каждого поля.

- [ ] Страница фичи оформлена по [Шаблону.Документация фичи](https://confluence.goldapple.ru/pages/viewpage.action?pageId=649174579), содержит ссылки на связанные спецификации без полного дублирования их содержания.
- [ ] В задачах на разработку приведены ссылки только на документацию, необходимую соответствующему исполнителю.

- [ ] Если часть затронутой документации осознанно не обновляется в рамках текущей задачи, для каждого отложенного обновления указаны конкретная страница документации и задача, в рамках которой будет выполнено обновление.
  - страница: …
  - задача: …



#### Требования к каждой затронутой спецификации

- [ ] Страница заполнена в соответствии с шаблоном: информация размещена в предназначенных для неё разделах; для незаполненных разделов указано «не применимо» и приведена причина.
- [ ] Для нового или изменённого поля / правила проверены связанные методы, контракты, версии и UI. Изменение отражено во всех спецификациях, без изменения которых заявленное в задаче поведение нельзя реализовать. Если метод, версия или экран сознательно не входят в объём разработки и сохраняют прежнее поведение, это указано явно.
- [ ] Если шаблон предусматривает описание алгоритма, то алгоритм описан либо указана причина его неприменимости. 
- [ ] Если одновременно используются схема взаимодействия и алгоритм, схема описывает участников и последовательность взаимодействия, а алгоритм — внутреннюю логику, шаги, ветвления, проверки и обработку ошибок.
- [ ] Для каждой страницы также выполнены требования разделов 1, 2, 4.



### 4. Качество требований

Требования этого раздела применяются к **каждой затронутой спецификации**.

#### Однозначность

- [ ] Нет формулировок, допускающих два и более прочтения. Ожидаемое поведение системы и результат понятны без дополнительного устного пояснения; для одного поля, параметра, настройки или сущности используется единое наименование во всех связанных спецификациях.



#### Полнота

- [ ] В документации отсутствуют незакрытые формулировки вида «будет описано позже» без указания ответственного и срока.
- [ ] Для каждого нового или изменённого атрибута указано, обязательный он или нет. 
- [ ] Для каждого нового или изменённого атрибута для состояний «нет поля / `null` / пустое», которые возможны на контракте, описано поведение: ошибка валидации, значение по умолчанию или иное явное правило. Если какое-то из этих состояний невозможно — это указано.
- [ ] Описаны применимые альтернативные и ошибочные сценарии: отсутствие данных, пустой ответ, недоступность системы, конфликт данных и другие актуальные случаи; они отражены во всех спецификациях компонентов, которые их обрабатывают при реализации этой задачи.



#### Принятые решения

- [ ] Все относящиеся к задаче замечания, вопросы и предложения из Jira, тредов и встреч обработаны: по ним внесены изменения либо дан аргументированный ответ и принято решение. Отдельное обсуждение на груминге для этого не обязательно, возможно обсуждение текстом / после дейли.
- [ ] Принятые решения отражены в спецификации на странице фичи; на странице метода — только если от решения изменяется контракт. 
- [ ] Для решений, влияющих на архитектуру, контракт, пользовательское поведение, надёжность или способ реализации, зафиксированы принятое решение и причина его принятия.



#### Непротиворечивость

- [ ] Связанные спецификации не противоречат друг другу: правила, значения и наименования одинаковы во всех местах, используемых для реализации и сопровождения решения.



#### Проверяемость

- [ ] По требованиям можно определить, как проверить ожидаемый результат: указаны исходное условие / точка входа, действие или условие срабатывания и ожидаемый результат.



#### Актуальность

- [ ] В затронутой документации нет неактуальной информации либо она явно обозначена как историческая / относящаяся к предыдущим версиям; планы дальнейших изменений соответствуют актуальным задачам и договорённостям.



#### Выполнимость

- [ ] Описанные сценарии и алгоритмы реализуемы во всех участвующих в задаче частях системы, не противоречат известным техническим ограничениям; выявленные ограничения и согласованный способ их учёта отражены в документации.



### 5. Задачи в Jira

- [ ] Задача заведена по утверждённому шаблону.
- [ ] Для клиентской доработки указан экран или точка входа и описано ожидаемое изменение поведения; если клиентской части нет — указан изменяемый backend-компонент или объект.
- [ ] Если объём или необходимость доработки различается по платформам, для каждой явно указано: требуется доработка / уже поддерживается / в рамках задачи не изменяется.
- [ ] Описание задачи содержит цель и ожидаемый результат; детальная реализация приведена в связанной спецификации, а ссылка ведёт на конкретный релевантный раздел либо позволяет однозначно определить необходимый исполнителю фрагмент.
- [ ] В testing-задаче содержится полный набор требований, необходимый для проверки результата: полное актуальное описание разработки либо отдельное описание тестирования без потери требований.
- [ ] Для backend-доработки заведена одна задача на изменение backend в рамках фичи со всей необходимой для реализации информацией.



### 6. Передача на ревью

- [ ] Чек-лист заполнен в текущей SA-задаче; каждый пункт, отмеченный `[x]`, подтверждается соответствующим изменением в задаче или документации.
- [ ] При повторном ревью обработаны все замечания предыдущего ревью: внесены изменения в документацию или задачу либо согласованное решение зафиксировано в документации.
- [ ] На момент передачи на ревью отсутствуют открытые вопросы; согласованные решения внесены в документацию.
