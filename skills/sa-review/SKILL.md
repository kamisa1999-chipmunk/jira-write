# SA-review

Техническая проверка SA-задачи по актуальному чек-листу. Пишет про состояние артефакта, не про автора. Не сочиняет спецификацию. Не публикует в Jira/Confluence без подтверждения.

Не ведёт историю качества по людям и не читает карточки сотрудников.

В пользовательском выводе — русские названия. Английские идентификаторы — только внутри модели. Не показывать технический лог (`Mode:`, `Verdict:`, `Confidence:`), если пользователь явно не попросил технический отчёт.

## Источники истины

Всегда читать файл с диска, не полагаться на память. Канон в этом репозитории:

```text
skills/sa-review/checklist-close-sa.md
```

Если у команды есть свой актуальный чек-лист — читать его, этот файл не дублировать в комментарии.

Jira-версия (копипаст в описание задачи) рядом: `skills/sa-review/checklist-close-sa-jira.txt`.

## Связка с другими скиллами

| Скилл | Когда |
|-------|--------|
| **этот** | Проверка аналитики, замечания, итог полноты проверки |
| `jira-write` | Только после подтверждения текста — комментарий в Jira |
| `jira-history` | Уровень 4: противоречие решений / неясная хронология ревью |

## Режимы

Технические идентификаторы: `self-check`, `review`.

| Идентификатор | Для пользователя |
|---------------|------------------|
| `self-check` | Самопроверка |
| `review` | Техническое ревью |

Что видит пользователь:

| Режим | Вывод |
|-------|--------|
| Самопроверка | Короткие зоны риска перед передачей |
| Техническое ревью | Полноценные замечания + основания для ревьюера |

> Ядро проверки общее, формат результата должен существенно различаться по режимам.

В выводе: `Режим: техническое ревью` — не `Mode: review`. Не ставить строку «Режим: …» в самопроверке.

### Самопроверка (`self-check`)

Аналитик проверяет свою работу до передачи на ревью.

Примеры: «проверь мою аналитику CAT2-4153», «проверь CAT2-4153 перед ревью», «сделай self-check», «проверь задачу по SA-чек-листу», «проверь, всё ли готово к ревью», «пройдись по чек-листу», «что я не учла», «посмотри аналитику перед передачей», «готова ли к ревью», «проверь спецификации».

- в Jira ничего не писать;
- не диагностический отчёт;
- один слой результата: 3–7 смысловых блоков, без дубля «подробно + ещё список»;
- формат и тон: [review-style.md](review-style.md) → Самопроверка.

### Техническое ревью (`review`)

Обычное техническое ревью.

Примеры: «сделай ревью CAT2-4153», «проверь CAT2-4153», «проверь аналитику», «поревьюй», «ревью SA», «проверь по чек-листу», «посмотри спецификации», «найди проблемы в аналитике», «подготовь замечания», «проверь документацию», «можно ли отдавать в разработку».

Если фраза неоднозначна между самопроверкой и техническим ревью — по контексту разговора. Нет контекста → техническое ревью (`review`).

## Порядок работы

```text
SA-review:
- [ ] Режим определён
- [ ] Jira-задача прочитана
- [ ] Чек-лист прочитан с диска
- [ ] Область изменений / карта изменения
- [ ] Связанные артефакты (уровень 2)
- [ ] Контекст фичи при необходимости (уровень 3)
- [ ] Решения / прошлые замечания при необходимости (уровень 4)
- [ ] Результаты проверки по применимым критериям
- [ ] Вывод по режиму (самопроверка ≠ отчёт ревьюера)
- [ ] (техническое ревью) ревью для ревьюера + итог полноты
- [ ] (техническое ревью) драфт комментария в Jira — не публиковать
```

### Шаг 1. Jira-задача

Из корня этого репозитория:

```bash
python3 scripts/cli/get_issue.py CAT2-XXXX
```

Прочитать из отчёта: summary, description, type, links, parent/epic при необходимости, комментарии про аналитику и прошлые ревью.

Связанные Development/Testing — только если уже заведены и нужны для пунктов чек-листа про задачи. Не читать весь проект. Не звать `get_issue_history.py`, пока уровень 4 не нужен.

Токены не читать и не показывать.

### Шаг 2. Чек-лист

Прочитать актуальный чек-лист целиком. Применять только релевантные пункты.

### Шаг 3. Область изменений

По Jira собрать внутреннюю карту (не вываливать в комментарий):

```text
фича
→ точки входа
→ компоненты
→ контракты
→ затронутая документация
```

Зафиксировать: цель изменения; платформы; экраны / точки входа; сервисы; методы; версии контрактов; события; БД / коллекции; админки; прочие компоненты.

## Поэтапная загрузка контекста

Не читать репозиторий «на всякий случай».

### Уровень 1 — обязательно

- Jira-задача;
- чек-лист;
- прямые ссылки из Jira.

### Уровень 2 — связанные артефакты

Открывать только страницы / спецификации / задачи, которые:

- прямо указаны в задаче;
- явно затронуты изменением;
- нужны для проверки связности (экосистема).

Confluence по `pageId`:

```bash
python3 skills/sa-review/scripts/dump_confluence_page.py PAGE_ID
```

Токен Confluence не читать. Страницу не изменять.

Не проверять только ту страницу, на которую аналитик дал ссылку, если изменение затрагивает связанные объекты.

### Уровень 3 — контекст фичи

Если в workspace есть заметки по фиче и они нужны, чтобы понять принятые решения — открыть только релевантный файл. Не читать все файлы фич.

### Уровень 4 — источник конкретного решения

Только при потенциальном противоречии: заметки груминга, история Jira, комментарий, связанная задача. Не собирать всю историю фичи без нужды.

## Что проверять

Внутренняя модель (не показывать эти ключи пользователю):

```text
criterion — проверяемый критерий
applicable — применим ли критерий к текущей задаче
expected_state — ожидаемое состояние артефакта
evidence — основание для вывода
verdict — результат проверки
gap — найденное расхождение
confidence — уверенность в выводе
```

### Результаты проверки

| Технический статус | Русское название | Что означает |
| --- | --- | --- |
| `OK` | Выполнено | Критерий применим и подтверждён найденными артефактами |
| `ISSUE` | Есть замечание | Найдено конкретное расхождение с критерием |
| `NEEDS_CLARIFICATION` | Требует уточнения | Данных недостаточно, чтобы достоверно подтвердить или опровергнуть выполнение |
| `NOT_APPLICABLE` | Не относится | Критерий неприменим к текущей задаче |

Во внешнем выводе: `Результат проверки: есть замечание` — не `Verdict: ISSUE`.

> Отсутствие найденного основания не означает автоматически «есть замечание».

Если состояние нельзя достоверно установить — «Требует уточнения» (`NEEDS_CLARIFICATION`).

Пункт чек-листа «не относится» без причины — не считается заполненным (это в самом чек-листе).

Не считать началом разработки доказательством качества аналитики. Не считать отсутствие вопросов от разработчиков доказательством полноты.

### Уверенность

| Значение | По-русски | Когда |
| --- | --- | --- |
| `high` | Высокая | Есть прямое подтверждение в Jira / Confluence / договорённостях |
| `medium` | Средняя | Вывод хорошо обоснован, но часть контекста косвенная |
| `low` | Низкая | Контекста недостаточно; предпочтителен статус «Требует уточнения» |

Во внешнем ревью: `Уверенность: средняя` — не `Confidence: high`.

- высокая — не выводить;
- средняя — выводить при необходимости;
- низкая — обязательно показать и, как правило, использовать «Требует уточнения», а не «Есть замечание».

## Экосистема изменения

Для изменённого объекта пройти связанные части:

```text
метод
→ версии
→ потребители
→ UI
→ связанные контракты
→ документация
```

Если меняется V2: существует ли V1; должен ли остаться неизменным; если да — это должно быть однозначно в аналитике. Не требовать изменение V1 автоматически.

То же: несколько платформ; несколько экранов; backend + frontend; BFF + SDK; HTTP + gRPC; producer + consumer.

## Решения

Если решение влияет на архитектуру, контракт, пользовательское поведение, надёжность, способ реализации или область изменения, проверить:

1. отражено ли само решение;
2. понятна ли причина, если она нужна дальше;
3. нет ли более нового решения, которое его заменило.

Если документация расходится с ранее согласованным решением, не считать автоматически одну сторону правильной. Формулировка:

```text
текущее описание расходится с ранее зафиксированным решением;
нужно либо привести артефакт к актуальному решению,
либо зафиксировать, что решение было пересмотрено.
```

Основание (даты груминга, цитаты) — только ревьюеру, не в Jira-комментарий.

## Замечания предыдущего ревью

Если задача уже была на ревью — каждое содержательное прошлое замечание.

Допустимо закрытым:

- исправлено в артефакте;
- принято другое решение и оно отражено в документации;
- замечание больше неприменимо из-за изменения области.

Недостаточно: ответить только в Jira; написать «сделано»; объяснить решение только в комментарии, если оно должно жить в спецификации.

Это не новое замечание, а незакрытое замечание прошлого ревью (`unresolved_previous_comment` / `unresolved_previous_review`) — см. [error-taxonomy.md](error-taxonomy.md).

## Стиль и форматы вывода

Обязательно следовать [review-style.md](review-style.md):

- состояние артефакта, не человек;
- внешнее замечание: где → что нельзя определить → какое состояние должно быть;
- не писать решение за аналитика;
- не перегружать контекстом;
- группировать, не комментировать каждый пункт чек-листа.

Порядок показа зависит от режима. Подробный диагностический разбор собирать внутренне всегда; наружу — только то, что нужно режиму.

**Самопроверка:** один слой по [review-style.md](review-style.md). Не показывать категории, уверенность, основания, статусы, «проверка завершена», счётчики замечаний. Основания раскрыть, только если спросили «почему ты так решил?».

**Техническое ревью:**

1. Ревью для ревьюера (с основанием, категорией; уверенность — по правилам выше).
2. Итог полноты проверки (ниже).
3. Отдельный компактный текст для Jira. Не публиковать. После подтверждения — скилл `jira-write` (`add_comment.py`, preview → `--apply`). Текст комментария не переписывать.

## Итог полноты проверки

Только для технического ревью. В самопроверке этот блок не выводить.

```text
Проверка завершена: да/нет

Проверено:
- Jira-задача
- N связанных страниц
- N контрактов
- контекст фичи: использован / не понадобился

Не удалось проверить:
- ...

Результат:
- замечаний: N
- требуют уточнения: N
```

Если нет проблем:

```text
Результат:
- замечаний не найдено
- уточнения не требуются
```

`Проверка завершена: нет`, если ключевые ссылки не открылись или применимый критерий остался без основания и без статуса «Требует уточнения».

## Ограничения

Нельзя:

- автоматически менять Jira;
- автоматически менять Confluence;
- придумывать решения и готовый текст спецификации;
- читать карточки сотрудников и личные заметки про людей;
- использовать прошлые ошибки автора, чтобы искать новые;
- читать весь репозиторий без необходимости;
- выдавать простыню контекста вместо замечания;
- дублировать чек-лист в комментарии.
