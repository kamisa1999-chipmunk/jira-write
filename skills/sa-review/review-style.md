# Стиль замечаний SA-review

Писать про состояние артефакта, не про человека.

## Плохо / хорошо

Плохо:

```text
Ты не учла V1.
Ты опять не описала null.
Ты проигнорировала комментарий.
```

Хорошо:

```text
В описании не зафиксировано поведение V1 после изменения V2.
Для null не описан ожидаемый результат.
Замечание предыдущего ревью в текущей версии документации не отражено.
```

## Формула одного замечания

Внутри скилла:

```text
проблема
+ основание
+ ожидаемое состояние
+ возможный способ устранения
```

Возможный способ устранения — только для внутреннего анализа. Не превращать его автоматически в инструкцию «исправь X на Y».

Во внешний текст (ревьюер видит короче; в Jira — ещё короче):

```text
где проблема
→ что из-за неё нельзя однозначно определить
→ какое состояние должно быть в результате
```

Обычно 1–3 предложения.

## Что не писать

Не использовать без необходимости:

```text
не соответствует чек-листу
недостаточно
неполно
неправильно
нужно доработать
переделай
исправь X на Y
замени это на это
```

Не потому что слова запрещены, а потому что они часто ничего не объясняют. Называть конкретный дефект.

## Не писать решение за аналитика

Не становиться автором спецификации.

Плохо:

```text
Добавь текст:
«V1 используется для старых клиентов,
V2 используется для новых клиентов».
```

Лучше:

```text
Из страницы неясна область применения V1 и V2. Должно быть однозначно зафиксировано, какие клиенты используют каждую версию.
```

Плохо:

```text
Сними label http и поставь grpc.
```

Лучше:

```text
Страница gRPC размечена как HTTP. Метаданные страницы должны соответствовать типу спецификации.
```

## Не перегружать контекстом

Скилл может знать подробную историю. В Jira-комментарий она не попадает автоматически.

Внутри:

```text
14.08 на grooming договорились A
21.08 уточнили B
текущая спецификация содержит C
```

В ревью / Jira:

```text
Текущее описание расходится с согласованным поведением для этого сценария. Нужно привести документацию к актуальному решению либо явно зафиксировать его пересмотр.
```

Основание — только ревьюеру.

## Группировка

Не делать комментарий на каждый пункт чек-листа. Связанные проблемы — одним блоком, например:

```text
Сценарии
Контракты и версии
Документация
Решения
Задачи разработки
Предыдущие замечания
```

Если одна проблема затрагивает несколько критериев — одно замечание.

## Формат для ревьюера

До комментария в Jira. Категория — русское название. Уверенность: высокую не показывать; среднюю — при необходимости; низкую — обязательно.

```text
## Ревью CAT2-XXXX

Режим: техническое ревью

### 1. Короткое название

Замечание:
...

Основание:
- Confluence: ...
- Jira: ...
- решение от ...

Категория:
Учет связанных компонентов
```

При средней уверенности добавить:

```text
Уверенность: средняя
```

Категории — в [error-taxonomy.md](error-taxonomy.md). При низкой уверенности, как правило, «Требует уточнения», а не «Есть замечание».

## Jira-комментарий

После подтверждения замечаний — отдельный компактный текст. Не включать: уверенность, внутренние категории, полный след оснований, цитаты чек-листа.

Не публиковать автоматически. Запись — через `jira-write`. Согласованный текст не переписывать.

Пример:

```text
По ревью аналитики есть несколько моментов.

1. В описании CAT2-4061 не разделены сценарии главной бренд-зоны и PLP/PDP. Из задачи нельзя однозначно определить, к какому экрану относится работа с V1, а к какому — V2. Сценарии нужно развести так, чтобы область изменения была понятна без дополнительного контекста.

2. В алгоритме gRPC смешаны уровни SDK и HTTP/BFF: logobarHeader/logobarFooter относятся к HTTP-контракту. На странице gRPC должно быть описано поведение именно SDK-метода.

3. Для новой версии метода не зафиксирована область применения относительно V1. Из документации должно быть понятно, какие клиенты используют каждую версию.
```

Тон ревьюера, не «агент нашёл».

## Самопроверка

Не:

```text
Замечание: отсутствует...
```

А:

```text
Перед передачей на ревью я бы ещё проверила:

- Для V1/V2 не зафиксирована область применения каждой версии.
- Для поля X нет поведения при null.
- В Jira-задаче не разделены сценарии Web и Mobile.
```
