# Sprint results

## Назначение

По завершившемуся или завершающемуся спринту CAT2:

1. собрать проверяемые факты из Jira;
2. прочитать цели и заметки со связанной страницы Confluence;
3. при наличии прочитать локальные материалы из `notes/sprints/`;
4. сопоставить обещанные цели с фактом;
5. написать готовый черновик сообщения для общего треда Mattermost.

Это не выгрузка Jira и не отчёт о занятости. Сообщение должно быть понятным бизнесу и IT: живым, коротким, содержательным.

По умолчанию только черновик. **Не публиковать** в Mattermost и **не изменять** Confluence/Jira.

Перед текстом прочитай [references/writing-guide.md](references/writing-guide.md) и эталон плотности в [examples.md](examples.md). Цели страницы задают приоритет, но отчёт строится по **всему составу спринта** (`issues` + `composition_candidates`). Запрещено оставлять в посте только цели Confluence, если в кандидатах есть значимая текущая или техническая работа.

## Отличие от sprint-review

| Скилл | Зачем |
|---|---|
| `sprint-review` | Ход активного спринта, риски, неназначенные, оценки |
| `sprint-results` | Итоговое сообщение широкой аудитории после/в конце спринта |

## Workflow

Скопируй и отмечай:

```
- [ ] Выбран спринт
- [ ] Собран context JSON
- [ ] Прочитаны заметки, фичи и конспект, если пользователь его дал
- [ ] Прочитан writing-guide и examples.md (эталон плотности, не копировать факты)
- [ ] Разобран composition_candidates по всему спринту, не только цели
- [ ] Матрица: цели + значимые не-цели (анализ, техника, текущие этапы)
- [ ] Черновик: прод + текущая работа + техника, не три цели
```

### 1. Выбор спринта

Явный `sprint id` из запроса — использовать его.

Если id нет:

1. найти на доске CAT2 спринт, дата окончания которого ближе всего к сегодня;
2. предпочитать уже закрытый или заканчивающийся сегодня;
3. если кандидатов несколько или выбор неоднозначен — показать их и спросить;
4. не брать молча активный спринт, если рядом есть только что закрытый.

Это делает CLI. Не выбирать спринт «на глаз».

### 2. Сбор фактов

Кэш: если по этому спринту есть context JSON младше 8 часов — читать его, скрипт не запускать. «Обнови / пересобери» или более старый файл → новый запуск. Старые отчёты не перезаписывать.

```bash
python3 scripts/cli/get_sprint_results_context.py --project CAT2
python3 scripts/cli/get_sprint_results_context.py --sprint-id 6162
python3 scripts/cli/get_sprint_results_context.py --sprint-id 6162 --refresh
```

Перед первым запуском: `pip3 install -r scripts/requirements.txt`.

CLI пишет timestamped JSON в `reports/`:
`{YYYY-MM-DD}_{HH-MM}__CAT2__sprint-results-{id}__{start}__{end}.json`.

Если `selection.status` не `chosen` — показать `candidates` и остановиться.

Если Confluence или локальные заметки в `missing_sources` — продолжить по оставшимся источникам и явно сказать, чего не хватило.

После CLI **обязательно** открыть в JSON:

- `confluence.sections.goals`
- `composition_candidates` (`groups`, `elogo_keys`, `standalone_tech_done_or_to_prod`, `present_keys`)
- при необходимости сами `issues`

Цели задают приоритет. Дополнительно просмотреть весь состав спринта и выбрать значимые продуктовые и технические результаты. Если `composition_candidates.groups` не пустой, а в черновике только цели страницы — отбор сломан, текст не показывать.

Не читать и не показывать токены из `.env`.

### 3. Источники и приоритет

Jira-статус карточки часто **отстаёт** от реальности (прод, FT, «уже выкатили»). Его нельзя называть актуальным этапом в посте без сверки с заметками и с пользователем.

Порядок смыслов:

1. **Слова пользователя и конспекты встреч** (если даны файл или «вот дейли») — что команда считает результатом.
2. **Локальные заметки** — `notes/sprints/`, `notes/features/` (план квартала и карточки фич этого спринта). Смысл, минимум/stretch, что сознательно не было целью, что уже в проде. Планы («хотим», «идеал», «stretch», «если успеем») не считать свершившимся фактом.
3. **Confluence** (`sprint.goal` → URL с `pageId` или `/display/SPACE/title`) — раздел `Цели` это обещания на старте. Их могли устно поправить на дейли. `Результаты` — контекст, не готовый текст для копирования.
4. **Jira** — состав работ и ключи, не истина про прод:
   - `Done` нельзя автоматически называть продом;
   - `To Prod` — готовность к релизу, не выпуск;
   - `Testing` / `To Test` — тестирование, не поставка;
   - если Jira говорит «ещё дизайн-ревью / To Test», а заметка или дейли — «живёт в проде», **не писать по Jira**. Зафиксировать расхождение и спросить.

При конфликте не угадывать и не усреднять.

### 4. Матрица и обязательные уточнения

Показать пользователю **до** любого черновика Mattermost:

| Цель/значимая работа | Связанные задачи | План | Факт | Состояние | Основание |
|---|---|---|---|---|---|
| ... | CAT2-... | ... | ... | одно из списка ниже | Jira / Confluence / заметка / дейли |

После сопоставления целей с Jira **ни одна значимая цель не должна молча исчезнуть**. Для каждой цели выбрать одно состояние:

- выпустили;
- подготовили к релизу;
- тестируем;
- завершаем разработку;
- начали разработку;
- завершили анализ или проектирование;
- перенесли;
- отменили.

В публичный текст не выводить состояния механически, но по каждой важной цели должно быть понятно, что произошло. Состояние в пост — только если этап подтверждён Jira, заметками, дейли или пользователем. `Done` ≠ прод.

Правила:

1. Связанные работы одной инициативы — один пункт, даже если часть уже в проде, а часть ещё идёт. Не дробить искусственно по статусам Jira.
2. Одна закрытая дочерняя задача не делает цель выполненной.
3. Значимое сверх целей клеить к той же инициативе, если это её следующий этап.
4. Не тащить обычные задачи без заметного результата.
5. Рутинные багфиксы — одна строка, только если вместе есть эффект.
6. Переносы — только если важны для ожиданий. Без виноватых, оправданий и внутренней кухни.
7. Нет подтверждённой причины переноса — не выдумывать её в пост.

Незавершённую инициативу **включать**, если верно хотя бы одно:

- она была целью спринта;
- за спринт завершён конкретный этап;
- работа перешла на следующий заметный этап;
- она важна для ближайшего релиза;
- команда уже активно готовит её к тестированию или завершает разработку.

Не исключать работу только потому, что она не в `Done` и не в проде. Не писать просто «в работе» / «продолжаем».

Формула незавершённого: `что удалось сделать за спринт → где сейчас → ближайший следующий этап`.

Перед черновиком — вопросы **одним списком** только по неподтверждённым фактам. Не переспрашивать то, что пользователь уже явно сказал.

### 5. Что попадает в сообщение

Ориентир обычного поста (не квота): 2–4 выпущенных или полностью завершённых результата; 1–3 значимые инициативы, которые существенно продвинулись; 1–2 технических улучшения с понятной пользой; переносы — только если важны для ожиданий.

Не заменять содержательность краткостью: нужна компактная и полная картина спринта, не минимальное число строк.

Попадает, если верно хотя бы одно:

- пользовательский или бизнес-результат;
- цель спринта — в любом из состояний выше;
- завершён или сменён заметный этап большой инициативы;
- работа важна для ближайшего релиза или уже идёт к тесту / концу разработки;
- техника с понятной пользой;
- перенос, который меняет ожидания.

Не включать автоматически: полный список тикетов, объём ради объёма, исполнителей, часы, testing-подзадачи отдельно от фичи, внутреннюю кухню.

### 6. Ответ пользователю

**Сначала** (пока нет подтверждения пунктов):

1. Краткая матрица цель → факт, с пометкой, где Jira расходится с заметками/встречей.
2. Компактный список вопросов: что включать, какой этап писать, какие ключи.

**Потом**, после ответов:

1. Готовое сообщение для копирования в Mattermost — без служебных оговорок и рассуждений агента.
2. Вопросы только если остались дыры; иначе коротко, каких источников не хватило.

Перед показом — самопроверка покрытия и текста из [writing-guide.md](references/writing-guide.md). Mattermost Markdown буквально: без обратных слешей перед `#` и `-`, без вложенных ссылок, URL одной строкой. Ссылка: `[CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)`.

## Чего не делать

- Не писать в Mattermost, не менять задачи, спринт, Confluence
- Не коммитить `.env`, отчёты и временные файлы
- Не придумывать факты, причины, эффект, Jira key, степень готовности
- Не называть `Done` продом
- Не подменять `sprint-review`
- Не делать фиксированную простыню разделов и не писать внутреннюю кухню в пост
