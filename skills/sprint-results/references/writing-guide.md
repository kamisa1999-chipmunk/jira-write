# Как писать итоги спринта

Финальный текст пишет агент. Python только собирает факты. Это сообщение тимлида для общей аудитории: и прод, и значимая текущая работа, и техника. Не выгрузка Jira и не список только целей страницы спринта.

Плотность и язык — [examples.md](examples.md). Факты эталона не копировать без сверки с JSON.

## Структура

Разделы динамические. Не фиксировать пять вечных блоков. Не создавать заголовок ради одного короткого пункта, если его можно вклеить в соседний.

Для насыщенного спринта допустимо:

```markdown
#demo #cat2 итоги DD/MM – DD/MM

<короткая живая подводка — только если звучит естественно>

### Выпустили
- ...

### Двигаем дальше
- ...

### Под капотом
- ...
```

Если одна инициатива сочетает выпущенный и новый этап — один пункт в наиболее подходящем разделе (часто «Выпустили», если главный результат уже у пользователей).

Не ставить `Launch` / `Delivery` / `Discovery` ради английского.

Порядок: пользователи и бизнес, затем крупные продуктовые этапы, затем техника без оправданий «зачем техдолг в спринте».

## Покрытие целей

После сверки с Jira ни одна значимая цель не исчезает молча. Внутренне у каждой цели одно состояние: выпустили / подготовили к релизу / тестируем / завершаем разработку / начали разработку / завершили анализ или проектирование / перенесли / отменили.

В пост состояния не копировать списком. Читатель должен понять, что случилось с каждой важной целью.

Перед текстом проверить:

- все ли цели спринта рассмотрены;
- разобран ли весь спринт (`composition_candidates`), не только цели;
- не исчезла ли важная работа только потому, что она ещё не `Done` или не была целью;
- указано ли, что конкретно сделали за этот спринт;
- понятен ли текущий этап;
- не попали ли обычные задачи без заметного результата;
- не раздут ли бизнес-эффект (не писать «готовы к любым новым акциям», если речь про включение механик для пользователей в России).

Ориентир объёма (не квота): 2–4 завершённых результата; 1–3 существенно продвинувшиеся инициативы; 1–2 технических улучшения; переносы — по необходимости. Не резать содержание ради трёх строк.

## Формула пункта

Завершённое: `что изменилось → зачем это важно`.

Незавершённое:

```text
что удалось сделать за спринт → где работа находится сейчас → какой ближайший следующий этап
```

Не писать «в работе» и «продолжаем работу». Конкретный этап — только если он подтверждён Jira или заметками.

Хорошо:

- `Начали второй этап Chanel — встраиваем e-logo. Завершаем разработку и готовим изменение к тестированию.`
- `Разработку сертификатов закончили на всех платформах, сейчас завершаем тестирование перед ближайшим релизом.`
- `Согласовали решение и оценки по лейблу 1+1 — задача готова к постановке в разработку.`
- `Фильтр по промокодам — на листинге теперь можно быстро найти товары, на которые действует массовый промокод.`

Одна инициатива может одновременно содержать готовый и продолжающийся результат. Не дробить по статусам.

Пример (только если все факты подтверждены):

`Запустили первый этап Chanel: Logo Bar и линия уже работают на сайте и в приложениях. Параллельно взяли в разработку второй этап — e-logo; сейчас завершаем разработку и готовимся к тестированию.`

Плохо:

- `Реализована задача по оптимизации взаимодействия компонентов системы`
- `Проведены работы в рамках техдолга`
- `CAT2-1234 — Done`
- `тест закрыт` / `отправили дальше к релизу` / `часть в мелкой доработке`
- искусственные метафоры вроде «второй этаж виджетов»
- обязательная шутка

Перевод Jira-языка:

- вместо «тест закрыт» — что проверили и к какому этапу готова работа;
- вместо «отправили дальше к релизу» — «подготовили к релизу»;
- вместо «часть в мелкой доработке» — конкретный достигнутый этап, если известен.

Не утверждать «выпустили», «включено на всех», «требование закона выполнено» без однозначного источника. Иначе сначала вопрос, не пост. `Done` не считать продом.

## Внутренняя кухня — не в пост

Не писать: «нашли дыру в анализе», «закрываем её сами», «техдолг в цели не пишем», виноватых, процессные конфликты, оправдания. Только внутренний контекст.

## Jira-номера

Только так, одной строкой, без пробелов и разрывов в URL:

`[CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)`

Добавлять, если пункт про одну основную задачу/эпик. Не добавлять во вводную и к testing-подзадаче. До трёх ключей. Не придумывать номер. Не вкладывать ссылку в ссылку.

## Технические задачи

Блок «Под капотом» — без вводных оправданий. Коротко практический эффект. Если польза не подтверждена — спросить, не сочинять.

Допустимые переводы только по сути задачи: миграция → проще сопровождать экран; лишний слой → меньше точек отказа; автотесты → быстрее регресс; обработка → меньше задержка; мониторинг → быстрее замечаем сбой.

## Язык

Русский, спокойный, уверенный. Живой язык — обычная речь и конкретные глаголы, не метафоры «для живости». Сначала результат, затем детали. PLP/PDP можно не объяснять. Без канцелярита и лозунгов.

Юмор не обязателен. Максимум одна лёгкая фраза из реального контекста. Нет — сразу результаты.

## Mattermost Markdown

Показывать текст буквально, готовым к копированию. В сыром результате запрещено:

- `\#demo`
- `\- пункт`
- `\[текст\](url)`
- вложенные `[текст]([url](url))`
- разорванные URL

Эталон:

```markdown
#demo #cat2 итоги DD/MM – DD/MM

- Результат. [CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)
```

## Самопроверка перед показом

- поймёт ли пункт человек вне команды;
- описан ли результат за спринт, а не активность;
- подтверждены ли степень готовности и эффект;
- все ли цели покрыты;
- не выпала ли незавершённая, но значимая работа;
- нет ли внутренней кухни;
- можно ли объединить пункт с соседним;
- не звучит ли текст как статус из Jira.

## Неопределённость

Неподтверждённые факты — одним списком. Не дублировать уже сказанное пользователем.
