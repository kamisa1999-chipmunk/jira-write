# Jira employee analysis

## Назначение

По сотруднику и периоду → CLI тянет задачи (включая историю assignee) → отчёт в `reports/employees/{employee}/` → ответ по JSON/Markdown.

Независимый источник **фактов** для последующей подготовки 1:1 / performance review. Сам по себе не пишет ОС и не сравнивает людей.

Отчёт — только факты из Jira. Карточки людей и другие личные скиллы не читать.

Токены Jira/Git не читать и не показывать. Модель `Issue` не менять. Старые отчёты не перезаписывать и не удалять.

## Примеры запросов

* Проанализируй работу Маши за последние два месяца.
* Что Рома делал в этом квартале?
* Обнови анализ Андрея.
* Покажи работу Ольги за июнь.

## CLI

Запускать из корня репозитория:

```bash
python3 scripts/cli/get_employee_analysis.py --employee Маша --months 2
python3 scripts/cli/get_employee_analysis.py --employee Андрей --quarter 2026-Q2
python3 scripts/cli/get_employee_analysis.py --employee Ольга --month 2026-06
python3 scripts/cli/get_employee_analysis.py --employee Маша --from 2026-05-01 --to 2026-07-01
python3 scripts/cli/get_employee_analysis.py --employee Андрей --months 2 --format both
```

Перед первым запуском: `pip3 install -r scripts/requirements.txt`. Скрипт может работать десятки секунд (много задач + changelog).

Имя файлов:

```text
reports/employees/{username}/{YYYY-MM-DD}_{HH-MM}__{period}.json
reports/employees/{username}/{YYYY-MM-DD}_{HH-MM}__{period}.md
```

Период по умолчанию — последние ~2 месяца, если не указан `--from/--to`, `--months`, `--month` или `--quarter`.

Имя сотрудника резолвится через Jira user search + `people_aliases` в `scripts/config/projects/CAT2.json`. Карточки людей **не читать**.

На этой Jira операторы `assignee was` / `assignee changed` возвращают HTTP 500. CLI берёт кандидатов через `assignee = user OR updated∈окно`, затем **фильтрует по changelog** — в отчёт попадают только задачи, где сотрудник был исполнителем в периоде (в т.ч. если сейчас назначен другой).

## Когда ходить в Jira

| Ситуация | Действие |
|----------|----------|
| Есть отчёт по этому сотруднику + тому же периоду **< 8 ч** | Читать JSON, скрипт не запускать |
| Уточнение по тому же анализу | Тот же отчёт |
| Отчёт старше 8 ч или «обнови / пересобери» | Новый запуск CLI → **новый** файл |
| Другой период | Новый запуск |

## Что показать в ответе

Разделить вывод на три части.

### Факты

Только показатели из Jira (`summary.facts`, агрегаты, список крупных задач). Не интерпретировать как эффективность.

Показать кратко:

* количество задач;
* завершённые и незавершённые;
* распределение по типам и направлениям;
* суммарную оценку и списанное время (с пометкой, что это issue-level);
* задачи без оценки / с превышением оценки;
* задачи с долгими этапами (в рабочих днях: пн–пт 10:00–18:00);
* возвраты после тестирования;
* carry-over между спринтами (только как гипотеза из смены Sprint);
* основные направления и наиболее крупные задачи.

Цифры — только из отчёта. Ссылки: `[CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)`.

### Повторяющиеся паттерны

Брать из `patterns[]`. Добавлять в ответ только если паттерн подтверждается несколькими задачами (уже отфильтровано в отчёте). Для каждого паттерна указывать задачи (`issue_keys`).

Примеры формулировок из отчёта:

* задачи регулярно долго находятся в Code Review;
* несколько задач возвращались после тестирования;
* сотрудник часто берёт задачи определённого направления;
* регулярно подключается к уже начатым задачам;
* работает преимущественно с большими задачами.

### Кейсы для ручного разбора

Брать из `review_cases[]`. Отдельно показать задачи, которые стоит посмотреть руководителю (несколько возвратов, долгое ревью, блокировки, частая смена исполнителя, много переходов статуса, значительное превышение оценки).

**Не делать** выводов о квалификации, мотивации или эффективности сотрудника только на основании Jira.

## Git-анализ

После построения Jira-анализа смотреть `git_offer`.

Если `git_offer.show == true` — **предложить** (не выполнять) дополнительный Git-анализ текстом из `git_offer.message`, например:

> Найдено 23 Merge Request за выбранный период.
>
> Могу дополнительно проанализировать:
>
> * количество замечаний на ревью;
> * категории замечаний;
> * повторяющиеся замечания;
> * циклы исправлений;
> * скорость реакции на ревью;
> * взаимодействие с ревьюерами.
>
> Выполнить Git-анализ?

Не выполнять Git-анализ автоматически.

Запускать его только после подтверждения пользователя:

```bash
python3 scripts/cli/get_employee_analysis.py --employee Андрей --months 2 --with-git
```

Для `--with-git` в `.env` нужен отдельный `GITLAB_PAT` (или `GITHUB_PAT`), не `JIRA_PAT`.

Если сотрудник не разработчик или связанных MR нет (`git_offer.show == false`) — предложение не показывать.

## Что читается из JSON

- `employee` — username, display_name, role, is_developer
- `period` — start / end / label
- `summary` — агрегаты, facts, notable_issues, by_type, by_direction
- `issues[]` — ключ, тип, статус, assignee_periods, оценки, этапы (workdays_in_*), returns, blocks, final_state
- `patterns[]` — id, title, detail, issue_keys
- `review_cases[]` — key, reasons
- `git_offer` — show, mr_count, message/reason
- `data_quality` — пропуски оценок, changelog, spent и т.п.
- `git` — только при `--with-git`

Важно: длительности этапов считаются **только** на пересечении статусов с периодами, когда сотрудник был исполнителем — не всей жизни задачи. Этапы — в **рабочих днях** (пн–пт, 10:00–18:00, 8ч = 1 раб. день; праздники не исключаются), не в календарных часах.

## Чего не делать

- Не использовать карточки сотрудников, заметки, историю one-to-one и другие скиллы
- Не писать готовую обратную связь
- Не формировать performance review
- Не сравнивать сотрудников между собой
- Не использовать количество задач как показатель эффективности
- Не просить токены и не коммитить `.env`
- Не менять `models/issue.py` / структуру `Issue`
- Не дублировать HTTP-клиенты
- Не запускать `--with-git` без явного согласия пользователя
- Не додумывать цифры, которых нет в JSON
- Не делать выводы о личности / мотивации / квалификации
