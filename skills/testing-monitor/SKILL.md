# Testing monitor

## Назначение

Разработческие задачи в `To Test` → CLI строит отчёт → JSON/Markdown в `reports/testing-monitor/` → ответ по снимку. Добавление в спринт — только через preview и `jira-write` после подтверждения.

Токен не читать и не показывать. Старые отчёты не перезаписывать. Не менять статусы, исполнителей и оценки без отдельного запроса. Не связывать задержку в `To Test` автоматически с работой тестировщика. Рекомендация по спринту — оценка ёмкости, не гарантия тестирования.

## Примеры запросов

* Покажи очередь теста / что в To Test
* Мониторинг тестирования / testing monitor
* Какие testing-задачи вне спринта?
* Куда добавить testing-задачи?
* Обнови очередь теста

## CLI

```bash
python3 scripts/cli/get_testing_monitor.py
python3 scripts/cli/get_testing_monitor.py --project CAT2 --format both
python3 scripts/cli/get_testing_monitor.py --config scripts/config/testing_monitor.yaml
```

Перед первым запуском: `pip3 install -r scripts/requirements.txt`.

Имя файла:

```text
reports/testing-monitor/{YYYY-MM-DD}_{HH-MM}__{PROJECT}__testing-monitor__sprint-{id}__{start}__{end}.json
```

Конфиг порогов и ёмкости: `scripts/config/testing_monitor.yaml`.

## Когда ходить в Jira

| Ситуация | Действие |
|----------|----------|
| Есть отчёт **< 8 ч** | Читать JSON, скрипт не запускать |
| Уточнение по той же очереди | Тот же отчёт |
| Отчёт старше 8 ч или «обнови / пересобери» | Новый запуск CLI → **новый** файл |
| «Добавь в спринт» / «примени» | Preview из отчёта → подтверждение → `jira-write` |

## Ручной контекст очереди

Перед ответом читать локальный `testing-queue-notes.md` в корне репозитория (если есть): исключения из «нашей» очереди, пакеты (типа beauties-store), блокеры (тестовые данные), договорённости. В сводке отделять «нашу» очередь от исключений; не предлагать тестировать пакет по одной ручке, если в заметках сказано ждать весь пакет. Обновлять файл, когда пользователь явно правит контекст («запомни», «убрала из очереди», «ждём данные» и т.п.).

## Что показать в ответе

1. Сводка: сколько в `To Test`, old/new flow, дольше порогов, вне спринта, рекомендации в текущий/следующий спринт
2. Учёт `testing-queue-notes.md`: наша очередь / исключения / блокеры
3. Ёмкость: очередь (задачи + часы), доступная ёмкость, качество данных / уверенность
4. **Качество прогноза** и **Требуют внимания** — если есть задачи без оценки
5. Риски по задачам (не весь список без запроса)
6. Блок `proposed_changes.preview_markdown` — если есть задачи вне спринта
7. Спросить: применить изменения через `jira-write`?

Ссылки: `[CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)`. Цифры — только из отчёта.

## Flows

### Старый (`label = old-test-flow`)

Сама разработческая задача — очередь на тест. Отдельные Testing не искать.

Показать: рабочие дни в `To Test`, assignee, спринт, приоритет, fixVersion, последняя активность, прошлые возвраты после тестирования.

### Новый (`label != old-test-flow`)

Связанные задачи типа `Testing`. Закрытые (`Done` / `Canceled`) игнорировать. Несколько открытых — норма (разные круги / платформы). Неоднозначность (`current_testing_task_ambiguous`) — только если нельзя понять, какая относится к **текущему** переходу в `To Test`.

## Выбор актуальной Testing-задачи

1. Взять связанные `issue_type = Testing`
2. Исключить закрытые
3. Восстановить входы разработческой задачи в `To Test` из changelog
4. Сопоставить каждую открытую Testing с кругом по **дате создания** относительно этих входов (не по похожему названию)
5. Актуальные = круг текущего (последнего) входа в `To Test`
6. Единственная открытая Testing из **прошлого** круга → `previous_open` + `testing_task_missing`, не актуальная
7. Открытые задачи прошлых кругов показать отдельно (забытые), не смешивая с актуальными
8. Если круг не определяется — `ambiguous`, риск `current_testing_task_ambiguous`

## Время в To Test

По changelog: текущий непрерывный период + число прошлых заходов. Рабочие дни пн–пт (праздники пока нет). Пороги: `warning_working_days`, `critical_working_days`.

## Ёмкость и спринт

```text
доступная ёмкость = оставшиеся раб. дни × hours_per_working_day × safety_factor × qa_count
загрузка = сумма remaining estimate активных testing в спринте
(нет remaining → estimate или default_issue_hours + допущение)
помещается, если оценка задачи + очередь ≤ доступная ёмкость
```

### Качество оценок очереди

Перед расчётом загрузки проверить каждую активную testing-задачу в очереди:

* есть ли оценка (QA/common hours, Original Estimate, Story Points);
* есть ли Remaining Estimate.

Если оценки нет:

* раздел **«Требуют внимания»**;
* риск `missing_estimate`;
* в расчёте — `default_issue_hours` с явной пометкой допущения.

Если в очереди есть задачи без оценки — раздел **«Качество прогноза»**: число, список, процент, уровень доверия. При доле ≥ `estimate_quality.missing_estimate_warning_percent` (по умолчанию 20%):

> Более 20% очереди тестирования не имеет оценки. Расчёт загрузки может быть неточным.

Расчёт загрузки всё равно выполняется. При любых допущениях прогноз **не считать точным** (`forecast_exact: false`).

Главный калибровочный параметр — `hours_per_working_day`. Сейчас консервативное значение; результат — рекомендация, не гарантия.

## Изменение Jira

Не добавлять в спринт автоматически.

Сначала показать preview из `proposed_changes.preview_markdown`. После «да / применяй» — `jira-write` / `update_issue.py` с `{"sprint": "<id или active или имя>"}` только для согласованных ключей.

Не менять статусы, исполнителей, оценки и прочие поля без отдельного запроса. Если следующего спринта нет — явно сказать и Jira не трогать.

## Риски в отчёте

`long_in_to_test`, `testing_task_missing`, `testing_task_not_in_sprint`, `testing_task_not_ready`, `unassigned`, `current_testing_task_ambiguous`, `release_risk`, `returned_after_testing`, `insufficient_capacity`, `insufficient_estimate_data`, `missing_estimate`

## Чего не делать

- Не перезапускать CLI при уточнениях по свежему отчёту
- Не обещать, что задача точно будет протестирована
- Не винить тестировщика за дни в `To Test`
- Не считать неоднозначностью сам факт нескольких Testing
- Не создавать unit-тесты ради этой фичи
- Не коммитить `.env`
