# Правила создания задач CAT2

Источник: репрезентативная выборка ~200 задач CAT2 за ~6 месяцев (Bug, DevelopmentB/F, Testing, Analysis, Design) + createmeta проекта. Ориентир на повторяющиеся паттерны, не на единичные аномалии.

Правила применяются скиллом `jira-write` при подготовке preview. В preview для каждого заполненного поля указывается **основание** (id правила ниже, например `R-SUM-01`).

Идентификаторы `customfield_*` не хардкодить здесь — маппинг в `scripts/config/projects/CAT2.json`.

---

## 1. Общие правила

| ID | Правило |
|----|---------|
| `R-GEN-01` | Проект по умолчанию: `CAT2`. |
| `R-GEN-02` | Не создавать задачу без обязательных полей типа (createmeta + таблица §5). |
| `R-GEN-03` | `budget` (Бюджет) обязателен у всех типов. Если пользователь не указал иное → default из project config: «Не заполнено» (`R-FLD-BUDGET`). |
| `R-GEN-04` | Priority по умолчанию: `Medium`, если пользователь явно не задал другой (`R-FLD-PRIO`). |
| `R-GEN-05` | `fixVersion` при создании **не** заполнять, пока пользователь явно не попросил. |
| `R-GEN-06` | Sprint заполнять только по явной просьбе («в текущий спринт», имя спринта). Иначе оставить пустым. |
| `R-GEN-07` | Epic Link заполнять только если пользователь назвал эпик/инициативу **или** однозначно следует из контекста (ключ CAT2-…). Не подставлять «популярный» эпик наугад. **Исключение:** плановый регресс → всегда `CAT2-3311` (`R-REG-08`). |
| `R-GEN-08` | Не выдумывать критерии приёмки, severity, env, платформу, **estimate**, assignee. |
| `R-GEN-09` | Preview → подтверждение → apply. Без подтверждения запись запрещена. |
| `R-GEN-10` | Платформа кодируется **и** в prefix summary, **и** в Component (кроме Testing — см. `R-TEST-03`). |
| `R-GEN-11` | Парную `Testing` к DevelopmentB/F/Bug **не** создавать и **не** предлагать: её заводит процесс/автоматика Jira. Создавать `Testing` только по явной просьбе («заведи testing», регресс). |
| `R-GEN-12` | Не создавать Epic / DeliveryStory / DiscoveryStory / LaunchStory по бытовым запросам «заведи задачу» — только если пользователь явно просит story/epic этого уровня. |
| `R-GEN-13` | **Estimate не выводить из правил и истории.** Часы ставить только если пользователь (или груминг) назвал оценку сейчас. Не подставлять «типичные» 10ч/16ч и т.п. Если оценка нужна, а цифры нет → `Q-ESTIMATE`. |

## 2. Выбор типа задачи

| ID | Сигнал в запросе | Тип Jira |
|----|------------------|----------|
| `R-TYPE-BUG` | баг, ошибка, «не работает», «ломается», дефект | `Bug` |
| `R-TYPE-BACK` | backend, бэк, API, BFF, сервис, Kafka, алерт, миграция либы на бэке | `DevelopmentB` |
| `R-TYPE-FRONT` | web, фронт, iOS, Android, UI, клиент, админка (фронт) | `DevelopmentF` |
| `R-TYPE-TEST` | «заведи testing» к уже существующей задаче (редко вручную) | `Testing` |
| `R-TYPE-REGRESS` | регресс, regress (плановый прогон Web/Mobile) | `Testing` (§3.4.1) |
| `R-TYPE-AUTOTEST` | автотест, написание/починка автотеста, e2e-кейс | `DevelopmentB` (§3.7); поддержка `data-test-id` → `DevelopmentF` |
| `R-TYPE-TESTCASE` | тесткейс(ы), тест-кейсы, test cases | `Documentation` (§3.8) |
| `R-TYPE-SA` | анализ, аналитика, SA, спецификация требований, ресерч аналитика | `Analysis` (спека документов → `Specification` только если явно «спека/тз») |
| `R-TYPE-DESIGN` | дизайн, макеты, Design | `Design` |
| `R-TYPE-DEBT` | техдолг, tech debt | `DevelopmentB` или `DevelopmentF` по платформе + prefix `[tech debt]` |
| `R-TYPE-DOC` | документация (не тесткейсы) | `Documentation` |

Если платформа неоднозначна (и бэк, и веб) — **спросить**, не угадывать (`Q-PLATFORM`).

Приоритет сигналов: регресс / автотест / тесткейсы распознавать **раньше**, чем общий «тест» → Testing.

## 3. Правила по типам

### 3.1. Bug

| ID | Правило |
|----|---------|
| `R-BUG-01` | Обязательны (кроме summary/project/type/budget): `severity`, `env`, `platform`. Без них preview `ready: false`, задачу не создавать. |
| `R-BUG-02` | Component = платформа бага (см. §7). |
| `R-BUG-03` | Summary: `[Prefix] <симптом>` — именная формулировка или «Не … / Некорректн… / Отсутствует…» (`R-SUM-BUG`). |
| `R-BUG-04` | Description — шаблон бага (§6.2). Без шагов/ожидания/факта — спросить недостающее (`Q-BUG-DESC`). |
| `R-BUG-05` | Парную Testing не создавать (`R-GEN-11`). |
| `R-BUG-06` | Severity/ENV/Platform маппить из текста, если однозначно; иначе спросить. Допустимые значения — §5. |

Типичные severity в выборке: Minor / Major (реже Trivial). Не ставить Blocker/Critical без явных слов пользователя.

### 3.2. DevelopmentF (web / iOS / Android / admin UI)

| ID | Правило |
|----|---------|
| `R-DEVF-01` | Prefix в summary обязателен: `[WEB]` / `[Web]`→ нормализовать в **`[WEB]`**, `[iOS]`, `[Android]`, `[AdminWeb]` / `[PlaidAdmin]` и т.п. (§7). |
| `R-DEVF-02` | Component: Web / iOS / Android / PlaidAdminWeb / MobileWeb. |
| `R-DEVF-03` | Summary: глагол в инфинитиве или отглагольное («Добавить…», «Перенести…», «Миграция…») (`R-SUM-DEV`). |
| `R-DEVF-04` | Description: Контекст / Что сделать / Ссылки; AC — только если даны (`R-DESC-DEV`). |
| `R-DEVF-05` | Estimate — только если пользователь назвал часы (`R-GEN-13`). |
| `R-DEVF-06` | При нескольких платформах — отдельная DevelopmentF на каждую. Testing не создавать (`R-GEN-11`). |
| `R-DEVF-07` | Label `web_platform` — только для явных миграций/работ web-платформы (перенос ручек frontBFF→webBFF и аналоги); иначе не ставить. |

### 3.3. DevelopmentB (backend)

| ID | Правило |
|----|---------|
| `R-DEVB-01` | Prefix: `[Back]` или имя сервиса `[brandzone]`, `[catalog.widgets-bff]`, … если так принято в контексте сервиса. |
| `R-DEVB-02` | Component: `Backend` (если не указано иное). |
| `R-DEVB-03` | Summary как у DevF: действие + объект (`R-SUM-DEV`). |
| `R-DEVB-04` | Description: цель/контекст + технические детали + ссылка на Confluence/тред при наличии (`R-DESC-DEV`). |
| `R-DEVB-05` | Testing не создавать (`R-GEN-11`). |
| `R-DEVB-06` | Если задача блокирует фронт — связь Blocks: backend → frontend (`R-LINK-02`). |

### 3.4. Testing

Парные Testing к dev/bug **создаёт автоматика** — через `jira-write` их не заводить (`R-GEN-11`).

#### 3.4.0. Ручной Testing к фиче (редко)

Только если пользователь **явно** просит создать Testing вручную (не регресс):

| ID | Правило |
|----|---------|
| `R-TEST-01` | Summary: `Testing ` + копия summary родительской задачи (включая `[Prefix]`). |
| `R-TEST-02` | Issue type: `Testing`. |
| `R-TEST-03` | Components и labels **обычно пустые** — не заполнять без просьбы. |
| `R-TEST-04` | Description: кратко суть/ссылка с родителя. |
| `R-TEST-05` | Assignee — только если сказали. |
| `R-TEST-06` | Epic — тот же, что у родительской задачи (если известен). |

#### 3.4.1. Регресс (`R-TYPE-REGRESS`)

| ID | Правило |
|----|---------|
| `R-REG-01` | Type: `Testing`. **Не** начинать summary с `Testing `. |
| `R-REG-02` | Summary (предпочитаемый актуальный формат): `Regress Web <дата>` или `Regress Mobile <даты> [(версия)]`. Допустимы legacy: `[WEB] Регресс <дата>`, `[IOS\|Android] Регресс мобилок <даты>`. |
| `R-REG-03` | Web и Mobile — **отдельные** задачи, даже если в одном релизе. |
| `R-REG-04` | Components обычно **не** ставить. Исключение: узкий тематический регресс (например Brandzone) — можно `QA`, если пользователь так хочет. |
| `R-REG-05` | Labels не ставить. |
| `R-REG-06` | Description: ссылка на TestOps launch и/или заметки «на что обратить внимание» (ФТ и т.п.) — только если даны. Пустое description допустимо. |
| `R-REG-07` | Часто клонируют прошлый регресс (`Cloners`) — если пользователь говорит «как прошлый» / даёт ключ, связать Cloners (`R-LINK-03`). Не искать прошлый ключ самостоятельно без запроса. |
| `R-REG-08` | Epic **всегда** `CAT2-3311` (Regress / Регрессы PLP). Не спрашивать, не оставлять пустым. |
| `R-REG-09` | Assignee — QA по запросу; иначе спросить или оставить пустым. |
| `R-REG-10` | Estimate — только названные сейчас часы (`R-GEN-13`). |

### 3.5. Analysis (системный анализ)

| ID | Правило |
|----|---------|
| `R-SA-01` | Prefix: `[SA]`. |
| `R-SA-02` | Type: `Analysis`. Component `SA` — желателен; ставить `SA`, если создаём «с нуля» по правилам. |
| `R-SA-03` | Summary: именная («Анализ…», «Актуализация…», «Доработка…», тема фичи) (`R-SUM-SA`). |
| `R-SA-04` | Description: цели / контекст / открытые вопросы / ссылки на БТ, Confluence, Figma (`R-DESC-SA`). |
| `R-SA-05` | Estimate — только если назвали часы (`R-GEN-13`). |
| `R-SA-06` | Testing не создавать (`R-GEN-11`). |

### 3.6. Design

| ID | Правило |
|----|---------|
| `R-DES-01` | Prefix: `[Design]` (или `[Plaid Admin Design]` для админки, если так сформулировал пользователь). |
| `R-DES-02` | Type: `Design`. Component: `Design` при наличии. |
| `R-DES-03` | Description: ссылка на Figma/требования + что нужно отрисовать/обновить. |
| `R-DES-04` | Testing не создавать (`R-GEN-11`). |

### 3.7. Автотесты (разработка)

Два разных сценария — не смешивать.

#### A. Написание / починка автотеста (`R-TYPE-AUTOTEST`)

| ID | Правило |
|----|---------|
| `R-AT-01` | Type: **`DevelopmentB`** (так в практике QA-автотестов CAT2), даже если речь про web/mobile web. |
| `R-AT-02` | Summary: `Написание автотеста <платформы> '<сценарий>'` **или** `[#<testopsId>][<PLATFORM>]<сценарий>`. Платформы в тексте: `WEB`, `MOB_WEB` / `MOBILE_WEB`, при необходимости обе. |
| `R-AT-03` | Labels: обязательно `autotest`; добавить `regress`, если кейс из регресс-набора; страны/темы (`ru`, `kz`, `kiosk`, …) — только если пользователь указал или они есть в исходном TestOps/описании. |
| `R-AT-04` | Components обычно **не** ставить (в отличие от feature DevelopmentB). |
| `R-AT-05` | Description: ссылка на TestOps test-case + шаги/expected (если даны). Без выдуманных шагов. |
| `R-AT-06` | Epic — только названный (часто QA/автотест-эпик). Не угадывать. |
| `R-AT-07` | Testing-пару не создавать (`R-GEN-11`). |
| `R-AT-08` | Estimate — только названные часы (`R-GEN-13`). |

#### B. Подготовка продукта под автотесты (`data-test-id` и аналоги)

| ID | Правило |
|----|---------|
| `R-AT-UI-01` | Type: **`DevelopmentF`**, component по платформе (обычно Web). |
| `R-AT-UI-02` | Summary как обычная DevF: `[WEB] Добавить data-test-id …` (допустимо начало `Автотесты. …`). |
| `R-AT-UI-03` | Labels `autotest` не обязателен; не ставить без нужды. |
| `R-AT-UI-04` | Description: какие элементы / какие id / где воспроизводится проблема. |

## 4. Правила по платформам

| Платформа | Prefix summary | Component | Bug.Platform (поле) | Тип разработки |
|-----------|----------------|-----------|---------------------|----------------|
| Web | `[WEB]` | Web | Web | DevelopmentF |
| Mobile Web | `[MOBWEB]` | MobileWeb (если нет в UI — Web) | `Mobile web ` (значение в Jira **с пробелом в конце**) | DevelopmentF |
| iOS | `[iOS]` | iOS | iOS | DevelopmentF |
| Android | `[Android]` | Android | Android | DevelopmentF |

Мультиплатформенный баг («на iOS и Android») → **две** задачи (или клон), не одна с двумя platform.

## 6. Шаблоны summary и description

### 6.1. Summary

| ID | Тип | Шаблон | Примеры (обезличено) |
|----|-----|--------|----------------------|
| `R-SUM-DEV` | DevelopmentB/F | `[Prefix] <Глагол/номинализация> <объект> [уточнение]` | `[WEB] Перенести ручку catalog/filters на webBFF`; `[Back] Добавить вызов MultiMediaApi.GetMedia` |
| `R-SUM-BUG` | Bug | `[Prefix] <Симптом без «баг:»>` | `[WEB] Не сбрасывается express при смене адреса` |
| `R-SUM-TEST` | Testing (к фиче) | `Testing [Prefix] <текст родителя>` | `Testing [WEB] Перенести ручку catalog/filters на webBFF` |
| `R-SUM-REG` | Testing (регресс) | `Regress Web <дата>` / `Regress Mobile <даты> [(ver)]` | `Regress Web 14.07`; `Regress Mobile 15.07-16.07 (6.13)` |
| `R-SUM-AT` | DevelopmentB (автотест) | `Написание автотеста …` или `[#id][PLATFORM]сценарий` | `Написание автотеста WEB + MOB_WEB 'Открытие оверлея…'`; `[#9737][MOBILE_WEB]Появление каунтера…` |
| `R-SUM-TC` | Documentation (ТК) | `Составить/Подготовить тест-кейсы для <фича>` | `Подготовить тест-кейсы для fast filters и sorting` |
| `R-SUM-SA` | Analysis | `[SA] <Тема анализа>` | `[SA] Анализ по добавлению нового фильтра Промокод` |
| `R-SUM-DES` | Design | `[Design] <Что сделать>` | `[Design] Обновление интерфейса страницы лейблов в админке` |

**Длина:** ориентир 40–80 символов, верхняя граница ~100–110. Не пихать в summary шаги воспроизведения.

**Плохие формулировки (избегать):**

- без prefix платформы (`Починить фильтры`);
- `Баг: …`, `Задача: …`, `TODO …`;
- расплывчато: `Доработки`, `Пофиксить`, `Разные правки`;
- несколько платформ в одном summary без раздельных задач;
- опечатки-якоря смысла («Некорретное», «Отсутсвие») — при создании писать грамотно.

**Грамматика:**

- Dev: чаще инфинитив («Добавить», «Перенести», «Доработать») или номинализация («Миграция», «Доработка»).
- Bug: симптом / «Не …» / «Отсутствует…» / «Некорректное …».
- SA: номинализация темы («Анализ…», «Актуализация…»).

### 6.2. Description — Bug (`R-DESC-BUG`)

Wiki-разметка Jira (как в реальных задачах):

```text
*Описание:*
<что не так, коротко>

*Окружение:*
Контур: <Prod / Preprod / Test>
Страны: <все / список>
[Браузер/устройство/сборка — если релевантно]

*Предусловия:*
# ...

*Шаги воспроизведения:*
# ...
```

## 7. Labels и components

### Components (обязательная практика для Dev/Bug)

| Сценарий | Component |
|----------|-----------|
| Web-клиент | Web |
| iOS | iOS |
| Android | Android |
| Backend / API / BFF | Backend |
| Админка Plaid | PlaidAdminWeb |
| Mobile web | MobileWeb |
| QA-регресс / плановый Regress | (пусто) |
| Автотест (написание кейса) | (пусто) |
| Тесткейсы Documentation | (пусто) |
| data-test-id под автотесты | Web (или платформа UI) |
| Системный анализ | SA |
| Дизайн | Design |
| MiniApp / WebView | MiniApp / WebView по тексту |

У Testing (в т.ч. регресс) и Documentation (тесткейсы) components по умолчанию не заполнять.

### Labels

| Label | Когда ставить |
|-------|----------------|
| `web_platform` | Миграции/работы web-платформы (перенос ручек BFF и т.п.) |
| `autotest` | Задачи на написание/починку автотеста (`R-AT-03`) |
| `regress` | Автотест из регресс-набора (вместе с `autotest`), если это следует из контекста |
| `testcase` | Documentation с тесткейсами (`R-TC-03`) |
| `old-test-flow` | **Не ставить** при создании новых задач |
| прочие страны/темы (`ru`, `kz`, `kiosk`…) | Только из текста пользователя / TestOps, не выдумывать |
| прочие | Только если пользователь назвал label явно |

Не изобретать labels «для красоты». Не копировать длинный набор labels с чужой автотест-задачи без запроса.

## 8. Правила связей

| ID | Связь | Когда |
|----|-------|-------|
| `R-LINK-01` | **Relates** DevelopmentB/F/Bug ↔ Testing | Создаёт **автоматика** вместе с Testing. Через write **не** создавать и не планировать в preview. |
| `R-LINK-02` | **Blocks** backend → frontend (и аналоги) | Бэк отдаёт API/контракт раньше клиента. |
| `R-LINK-03` | **Cloners** | Баг/задача на вторую платформу; **регресс** «как прошлый» (если дан ключ предыдущего). |
| `R-LINK-04` | **Sub task / Main task** | Связь с DeliveryStory / родительской story — только если story известна. |
| `R-LINK-05` | **Parent-Child** | Явная иерархия parent/child. |
| `R-LINK-06` | **Duplicate** | Только если пользователь говорит «дубликат». |
| `R-LINK-07` | **Dev Design** | Дизайн ↔ разработка, если пользователь связывает. |

Порядок в batch: сначала создать issues, затем links (`create_issue.py --batch`).

Типовой пакет фичи (через write):

1. `[Back] …` (DevelopmentB)  
2. `[WEB] …` / `[iOS] …` / `[Android] …` (DevelopmentF)  
3. links: Back **blocks** Web (если есть зависимость)  
4. Testing к каждой dev/bug появится автоматически — в пакет не включать

## 10. Неоднозначности — спрашивать у пользователя

Коды вопросов для preview:

| Код | Когда спрашивать | Не спрашивать, если |
|-----|------------------|---------------------|
| `Q-TYPE` | Неясно Bug vs доработка vs анализ | Явный тип/глагол «баг/анализ/бэк» |
| `Q-PLATFORM` | Несколько платформ или не названа | Одна платформа в тексте |
| `Q-BUG-SEV` | Bug без severity | Однозначно из «блокер/мелочь» |
| `Q-BUG-ENV` | Bug без контура | Указан прод/препрод/тест |
| `Q-BUG-PLAT` | Bug.Platform не выводится из prefix | Prefix однозначен |
| `Q-BUG-DESC` | Нет шагов или ожидания/факта | Пользователь дал полный баг-репорт |
| `Q-EPIC` | Нужна привязка к инициативе, ключ не назван (не регресс) | Ключ эпика/story есть в тексте; **для регресса** epic всегда CAT2-3311 — не спрашивать |
| `Q-ASSIGNEE` | «Назначь на …» без алиаса в config | Алиас есть в CAT2.json |
| `Q-ESTIMATE` | Нужна оценка в задаче, цифры нет; или пользователь ждёт estimate в preview | Часы названы **сейчас** — не подставлять из прошлых задач |
| `Q-TESTING` | Пользователь явно просит Testing вручную, но неясен parent/scope | Для обычных Dev/Bug Testing не предлагать — она авто |
| `Q-REGRESS` | «Заведи регресс», но не ясно Web vs Mobile / даты | Платформа и даты названы |
| `Q-AUTOTEST` | Неясно: написать автотест (DevB) vs data-test-id (DevF) | Явно «напиши автотест» или «добавь data-test-id» |
| `Q-TESTCASE` | «Тесткейсы», но нет фичи/scope | Фича и границы названы |
| `Q-BUDGET` | Нужен конкретный бюджетный бакет | Оставляем «Не заполнено» |
| `Q-SCOPE` | «Доработки по X» без границ объёма | Объём перечислен |

Минимум вопросов: только то, без чего `ready: false` или без чего нельзя выбрать тип/платформу.

## 11. Как показывать основание в preview

Для каждого поля в ответе пользователю:

```text
Поля:
- issue_type: DevelopmentF  ← R-TYPE-FRONT (в запросе: «web»)
- summary: [WEB] …          ← R-SUM-DEV + R-DEVF-01
- components: [Web]         ← таблица платформ §4
- budget: Не заполнено      ← R-FLD-BUDGET / defaults
- severity: ?               ← Q-BUG-SEV (обязательно для Bug)
```

Блок «Не создаём, пока не закрыто:» — список missing required + коды `Q-*`.

## 12. Источник и ограничения анализа

- Выборка: поиск CAT2 `created >= -180d` по основным типам (~200 задач) + точечный raw-fetch полей.
- Components/epic/severity в нормализованных search-отчётах раньше не попадали в модель — статистика fill-rate уточнена raw API.
- Частотный эпик в данных не использовать как default.
- Правила для DeliveryStory/релизов не формализованы — при запросе на story верхнего уровня уточнять у пользователя отдельно.
